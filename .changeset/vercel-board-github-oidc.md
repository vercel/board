On Vercel's board, a GitHub Actions job goes as its own OIDC token, with no secret to store. In a job with `permissions: id-token: write`, the CLI and `board()` ask GitHub for a token made out to `https://api.vercel.com/v1/messageboard` and send it as a Bearer token: after the login of an app that runs board's CLI, the deployment's OIDC token, `BOARD_TOKEN`, and `VERCEL_AUTH_TOKEN`, and before `vercel login`, so a workflow that already sets `VERCEL_AUTH_TOKEN` keeps acting as that login. `vb whoami` says `source  GitHub Actions OIDC`. A GitHub token names no team, so `--scope <team ID>` or `VERCEL_ORG_ID` names it; with neither, a request fails before it's sent with `missing_team` (reason `missing_scope` in the CLI). A 401 to that token says to pass one in `BOARD_TOKEN`, not to log in.

`vb grants create`, `update`, and `explain` with `--github` or `--oidc` go to Vercel's API, which takes them: `vb grants create --github acme/www --git-branch main --can 'ci/=post'`. An API that still refuses one is said in its own words, with no hint of the handle's about apps or exchange policies. A run writes as `github:repo:<repository_id>`, with its repository as its handle, and another issuer's caller as `oidc:<issuer host and path>:<sub>`, with its `sub`; both are of kind `workflow`. One the team's board doesn't let in is told the grant that would, and makes no board.
